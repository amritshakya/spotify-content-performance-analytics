  Reproduce it locally with `python -m src.load_data --copy-from <path-to-original-spotify.csv>`
  or simply by copying the file yourself into `data/raw/spotify.csv`.

  running `src/clean_data.py` and `src/build_database.py` (see repository root README for the

## Provenance status

The CS251 course materials (`project02/exploratory_data_analysis.ipynb`, assignment description)
state that the dataset was *"collected from the Spotify music service ... obtained using its
[web API]"*. That statement is the course's own description of the data, provided to students
alongside the CSV — it has **not been independently verified** by this project (no original
API pull, request log, or collection script accompanies the extract). Accordingly, this project
treats provenance as:

> Spotify-sourced dataset supplied for CS251 coursework, described by the course as collected via
> the Spotify Web API. The exact collection date, query parameters, and sampling frame used to
> assemble this ~278K-row extract were not independently verified and are not recoverable from the
> file itself.

Do not upgrade this to an unqualified "collected via the Spotify Web API" claim in downstream
writing — always attribute it to the course description.

## Known sampling limitations

- **Unknown collection time.** `popularity_score` is Spotify's algorithmic popularity metric,
  which reflects recent play volume and recency *as of whatever moment the data was pulled*. That
  moment is not recorded anywhere in the file and must **not** be inferred from filesystem
  timestamps (those reflect when this course's copy was written to disk, not when Spotify was
  queried).
- **Unknown, likely non-random sampling frame.** There is no evidence this extract is a random or
  representative sample of Spotify's catalog. Every share/percentage figure in this project is
  therefore scoped explicitly to "tracks in this dataset," never generalized to "Spotify" broadly.
- **Zero-popularity mass.** ~16.9% of tracks have `popularity_score == 0`, and the bottom of the
  distribution is comparatively sparse below the median (see `reports/data_quality_report.md`).
  This pattern is *consistent with* the extract having been pre-filtered or otherwise
  non-randomly assembled — it is reported as suggestive evidence, not proof.
- **`artist_2` / `artist_3` are 100% missing** in this extract and are documented as unusable
  collaborator fields (see cleaning policy in the root README / data-quality report).
- **Genre availability is not random.** Tracks with a populated `artist_1_genre_1` differ
  systematically from tracks without one (higher popularity, higher `artist_1_pop`) — see the
  genre-availability bias analysis in `reports/data_quality_report.md`. Genre-conditioned claims
  throughout this project are phrased as "among tracks in this dataset with an observed primary
  genre," not as unconditional statements about all tracks.
- **`artist_1_pop` is entangled with track popularity`,** not an independent predictor of it —
  documented wherever it is used as a feature.

## Course-specific row-2 type declarations

Row 2 of the raw CSV declares each column's course-assigned type (`string`, `numeric`, or
`categorical`). These types describe how the *original CS251 NumPy `Data` class* parsed the file
and do not necessarily match the pandas dtypes this project infers. The loader skips this row
entirely (`skiprows=[1]`) rather than trying to reuse it.
